# D2R Mobile：实验性 iOS 17 / A16 兼容

[jhaizhou-ops/d2r-mobile](https://github.com/jhaizhou-ops/d2r-mobile) 的非官方兼容分支，保留上游历史、署名与 MIT 许可证。目标是把上游 M3 路线适配到 iOS 17，不是重新实现游戏，也不代表暴雪或上游的官方支持。

## 当前基线：1.0.18 / build 2026102408

本次同步把 iOS17/A16 运行时的累计工作推进到本地已真机核验的 **build 2026102406**，版本号升到 1.0.18。

### 本次同步内的性能工作（iPhone 14 Pro Max / iOS 17.0 真机核验）

- **动态 3D 比例下限降到 0.55**（build 2026102403）。重度战斗里旧下限 0.60 仍让 GPU 跑到 18–20.5 ms（预算 16.7 ms）；现在只有 0.60 持续掉帧时控制器才降到 0.55，之后自动回升。UI 与文字比例不动。同路线真机 A/B：上屏掉帧 **8.4–8.8% → 3.54%**，最差 10 秒窗 **63.7% → 15.3%**，重度战斗 58.7–60 fps，GPU p95 9.8–14.9 ms。
- **驱动段常量精确填充**（build 2026102404）。命令翻译层原先每次着色器启动都整段清零 0xA00 字节驱动段并做 272 次表拷贝。离线反射（`nvn_refl`）现在记录每个着色器实际读哪些 vec4 槽（着色器 JSON 的 `drv_reads`，常量下标、上限 10 槽）；热路径只填这些槽。全库 6,927 个着色器中 2,795 个读驱动段，全部常量下标、每着色器 1–10 槽。旧 JSON 没有偏移信息时回退整表填充。
- **内存池地址查找免锁**（build 2026102405，2406 修复）。`mtl_addr`/`mtl_gpu_addr` 原先每次查找都拿全局池锁并线性扫全部池（每帧数万次）。seqlock 快照（`pool_snap_publish`/`pool_snap_find`：偶数代 = 完整可用，奇数 = 写入中）让稳态查找免锁。2405 的快路跳过了首次驻留登记，真机紫屏；2406 要求池先走过一次加锁慢路（驻留集 + 老接口绑定表登记 + arena 提交）才允许快路命中，快照改为 1024 定长数组（无锁读者扫到一半 realloc 换地址是释放后使用；真超上限就作废快照全员走慢路）。
- **2406 真机核验**：`【红】`绑定类红字 0 条（2405 紫屏证据类）。本局提交 CPU 每帧较 2403 基线下降（该局中位 ≈2.7 ms vs ≈5.2 ms），GPU p95 尾段改善（10.9–12.0 ms vs 11.9–14.9 ms）。注意：2406 这局前半程在 0.75 档跑更重的场景（进程 CPU 231% vs 2403 局的 205%），两局的总掉帧百分比**不可直接对比**；公平的同路线 A/B 仍待采集。

### 诊断开关（App 的 `Documents/` 目录，「文件」App 里可见）

| 文件 | 作用 |
|---|---|
| `dm_sample.txt` | 主线程 PC/回溯采样器。`0`/`off` 关闭；数字 = 间隔毫秒（缺省开、10 ms）。采样器会按间隔向客体主线程发信号——采干净的性能数据前先写 `0` 关掉。 |
| `diagnostics_profile.txt` + `diagnostics_build.txt` | 测量档（`timing`/`gpu`/`display`/…）。构建号文件与当前运行构建不一致时忽略，按普通游玩处理。 |
| `log_sync_profile.txt` | `baseline` = 逐行同步落盘；其他 = 缺省的环形队列批量写。 |

### 沿自先前同步

- 逐编码器 Metal3 资源声明、泛光/系统 UI 快照保护、GPU Scheduled 后直接呈现。
- 省电 30 帧周期修正与呈现票号一致性。不是插帧；请求 60 Hz 不保证系统回调必达。
- 主运行环 60 Hz `NSTimer` 输入/UI 轮询，与渲染 30/60 无关。
- 可选的逐线程 CPU 时间与呈现/通道诊断；普通模式不启用额外收集器。

**实验性质：30 帧档残余卡顿、延迟与发热未宣称修复。** 上面的 2403/2406 数字来自 iPhone 14 Pro Max（A16，iOS 17.0）单机、温控 0 档下的运行；其他设备、长局与全部场景未验证。宿主/静态检查不等于 A16 性能；GPU 命令时长求和不是利用率也不是整机功耗。
